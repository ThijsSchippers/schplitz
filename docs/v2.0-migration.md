# Schplitz v2.0 — moving existing tallies

Status: draft · October 2026 · companion to [v2.0.md](v2.0.md)

Goal: **nobody loses a tally, and nobody sees a balance they don't recognise.** Every v1 tally moves into v2 with its history and balance intact. The two phones in a tally end up in the same v2 tally without having to coordinate the upgrade.

---

## 1. What exists today

This inventory is based on the git history of `src/App.jsx`.

### 1.1 On people's devices (origin `https://schplitz.com`)

| Shape | Written by | Contents | Notes |
|---|---|---|---|
| **A1** `localStorage.schplitzExpenses` | 28 Mar 2026 → now | `initialized, myName, otherName, securityQuestion, statuses, settlements, expenses[]` | `settlements` added 9 Apr. The current shape. |
| **A2** same key | 11 Feb → 28 Mar 2026 | as A1, **plus `securityAnswer` in plain text**, no `settlements` | Today's app rewrites the key without the answer on first load. So A2 only survives on devices **not opened since 28 March**. |
| **A3** same key | 10 Feb 2026 (one day) | `{ myName, expenses }`, no `initialized` | Already ignored by today's app. `paidBy` could be either person. Most likely only test data. |
| `sessionStorage.schplitzAnswer` | 28 Mar → now | the normalised answer | Lives per tab. Not reliable for migration. |
| `sessionStorage.schplitz_launched` | — | `"1"` | Landing-page flag. Ignore. |

Each expense is `{ id, description, amount, currency, paidBy, date }`:

- `amount` is a JS float.
- `currency` is one of EUR, USD, ALL, AED, NOK, SEK, THB.
- `paidBy` is a **name**, not an ID.

### 1.2 In chat histories

| Format | Created | Still importable today |
|---|---|---|
| `#share=` **v4** (deflate, then encrypt) | 9 Apr 2026 → now | yes |
| `#share=` **v3** (plain JSON, then encrypt) | 11 Feb → 9 Apr 2026 | yes |
| Pasted text export (v3/v4 JSON) | when a link would exceed 8,000 chars | yes |
| v1 / v2 text exports | 10 Feb 2026 | **no**, dropped on 11 Feb. Not supported in v2 either. |

Links live in chat histories forever. People will tap old ones after v2 ships.

### 1.3 Facts that make migration easier

1. **Since 11 Feb, every expense was added by the person who paid it.** `addExpense` sets `paidBy: myName`. v2's rule ("you only write your own entries") therefore maps onto v1 data directly.
2. **Expense IDs survive sharing unchanged.** Import keeps `e.id`, so the two phones' copies can be matched entry by entry.
3. **Every ID starts with its creation time.** `uid()` = `Date.now().toString(36)` + random. That gives an order for entries and an age for any snapshot, including old links.
4. **One tally per device.** v1 can't hold more, so migration creates at most one v2 tally per device.
5. **Everyone switches at once.** There is no app store and no service worker: after deploy, every device runs v2 on its next page load. Mixed versions only come from old links and browser tabs left open.
6. **The local data isn't encrypted.** Migration can run immediately on first load, without asking for the answer.

### 1.4 What makes it hard

| # | Risk | Why |
|---|---|---|
| R1 | **The two phones disagree** | v1 import *replaces* the list, so each phone holds "the last snapshot it received + its own additions since". Deletions only travel inside full snapshots, and either person could delete the other's entries. |
| R2 | **The phones must end up in the same v2 tally without talking first** | v2 routes links by `tallyId`. If each phone invented a random one, their first v2 links wouldn't match. |
| R3 | **Tallies that were already settled in real life** | v1 can't record a payment. A tally where both were "done" and money changed hands may still be on the phone, and would show a stale balance in v2. |
| R4 | **Old links tapped after the upgrade** | A v1 link is a full snapshot. Importing it the v1 way would bring back deleted entries and overwrite newer data. |
| R5 | **The answer isn't stored** | It's needed to derive the v2 key. Only A2 devices still have it on disk. |
| R6 | **Free-text descriptions** | v2 doesn't sync free text, but people still want to recognise their history. |
| R7 | **Settlement messages may contain IBANs** | They mustn't be synced or shown more widely than before. |
| R8 | **Rates and rounding** | v1 converts at view time with historical rates and floats. v2 locks rates per entry in integer cents. |
| R9 | **Storage is per origin** | v2 must run on exactly `https://schplitz.com`. `www.` or a subdomain can't see v1 data. |
| R10 | **Data already lost** | Safari's 7-day deletion or cleared site data may already have wiped one phone. |
| R11 | **Rollback** | If v2 has to be rolled back, v1 must still find its data. |

## 2. The plan

### No bridge release

v2 ships directly, with no v1.x release in between. The permanent *Bring in an old tally* option (step 6), with old links as full copies, the welcome screen's "already squared up?" question (step 2), and the chat-as-database design in v2 cover what a bridge release would have done.

**Optional:** if v2 is still months away, fix the one active data-loss bug in v1 on its own: warn before opening a link removes entries that haven't been shared yet (R1).

### Step 1 — Silent local migration (first v2 load, no prompts)

1. Read `schplitzExpenses`. Accept A1 and A2. Leave A3 untouched.
2. Validate every expense with `validateExpense`. Invalid ones go to a local "couldn't read" list shown in Details. They are never silently dropped.
3. Create a local v2 tally with a **local ID**, not yet synced, and two members from `myName` / `otherName`.
4. Convert expenses:
   - `paidBy === myName` → **my legacy log**, ordered by ID timestamp, `seq` 1…n, keeping the v1 `id` as `legacyId`.
   - `paidBy === otherName` → **provisional copy** of the other person's entries. It's shown and counted, but replaced at the handshake (step 3).
   - Any other `paidBy` (hand-edited data) → an "unassigned" list for review.
   - `amount` → integer minor units, `Math.round(amount × 10^decimals)`.
   - `description` → category **Something else** for every legacy entry, with no guessing. The original text is kept as a **private note on this device**, so history stays recognisable (R6). People sort their own entries afterwards (step 2b).
   - **Lock rates:** the historical rate for each entry's date, exactly what v1 shows today. AED/ALL, or any offline fallback, is marked *estimated* (R8).
5. `statuses` are dropped. `settlements` messages become a local, read-only note in Details: *"Before the upgrade, Sofia wrote: …"*. They're never synced (R7).
6. **A2 devices:** use the stored `securityAnswer` to derive the sync key straight away (step 3), then **delete the plain-text answer**.
7. Leave `schplitzExpenses` **untouched** for rollback (R11). Store a fingerprint of it next to the migrated tally.
8. Call `navigator.storage.persist()`.

Migration is **idempotent**: it is keyed by the fingerprint, so running it twice changes nothing. If the v1 key changes later (a v1 tab left open somewhere), only new IDs are imported.

### Step 2 — Welcome screen (first open after migration)

One screen:

> **Your tally with Sofia came along.**
> All 86 entries are still here. The exact amounts are in Details.
>
> *Did you and Sofia already square up for this tally?*
> **[ Yes, start fresh from here ]**  **[ No, keep the balance ]**
>
> Old entries are filed under *Something else* for now. *Sort them* whenever you like.

- **"Start fresh"** records a `cfg` flag: *legacy entries are history only and don't count toward the balance.* It's a flag, not an amount, so if both people choose it, it isn't counted twice, and it doesn't depend on the two phones agreeing on the old balance.
- **"Keep the balance"** carries everything over, which is the default.
- **If the two people choose differently**, both see *"Sofia started fresh from the old tally"* with **Undo**. Last choice wins (normal `cfg` rules). It's a conversation between friends, not a lock.

### Step 2b — Sorting old entries (optional, any time)

All legacy entries start as *Something else*. Sorting them is optional and never blocks anything.

- **Where:** a link on the welcome screen (*"Sort your old entries"*) and a permanent **Details → Sort old entries**.
- **Grouped by the old text.** One row per distinct description, with your own entries only: *"koffie" · 14 entries*, *"Padel Sunday" · 6 entries*. Under each row are the category tiles. **One tap sorts the whole group**, and single entries can still be changed in Details.
- **You sort your own entries.** The payer decides, as everywhere in v2. You can see the old text of the other person's entries, but not change their category. When they sort theirs, it syncs to you.
- **Sync:** one tile tap = one compact `recat` entry (category + list of `seq` numbers), so sorting a hundred entries adds only a few hundred characters to the next link.
- **Social units** only use sorted entries (Something else never counts as a unit). "About 2 coffees" works as soon as people sort, or once new entries come in.

### Step 3 — Handshake: the first v2 sync between the two phones

**Same tally ID on both phones without coordination (R2).** On the first share (or receive), ask for the answer **once**, unless A2 already provided it. Then:

```
master  = PBKDF2-SHA256(answer, salt = "schplitz-v1|" + question + "|" + sortedNames, 200k)
tallyId = HKDF(master, "tally-id")      key = HKDF(master, "enc")
memberId(name) = HKDF(master, "member|" + name)
```

Both phones hold the same question, names and normalised answer, so they derive the same `tallyId`, key and member IDs independently. New v2 tallies (not migrated) keep using random IDs.

**Typo protection.** A wrong answer gives a different `tallyId`. The receiving phone sees an unknown tally whose plaintext question matches its own not-yet-synced migrated tally. It tries its own key, decryption fails, and it shows: *"This is Liam's upgraded tally, but your answers don't match. One of you typed it differently."*

**The first link** from a migrated tally carries:

- the sender's **whole legacy log** (authoritative),
- its **provisional copy** of the other person's entries (marked provisional),
- a `legacy-handshake` marker.

The legacy log is folded into each person's summary straight away, so the balance travels in every link from then on. The line items themselves go in the handshake link if they fit the 2,000-character budget (about 11 chars per entry), otherwise as a full-copy file.

### Step 4 — Reconcile, entry by entry, by v1 `id` (R1)

The rule is the v2 rule: **the payer's phone decides about the payer's entries.**

| Situation (seen on my phone) | Most likely cause | Result |
|---|---|---|
| Sofia's entry: in her log, not in my copy | She added it after her last share | Added |
| Sofia's entry: in my copy, not in her log | She deleted it | Removed |
| My entry: in my log, not in her copy | I added it after my last share, **or** she deleted it in v1 | **Kept**, and listed for review: *"Sofia's phone didn't have these 2 of yours. Keep them?"* |
| My entry: in her copy, not in my log | I deleted it | Stays deleted |
| **My phone has no legacy data at all** (wiped, R10) | Data loss | *"Restore 23 of your entries from Sofia's phone?"* → her copy is adopted as my legacy log |

Afterwards, each person sees a one-time summary only if something changed: *"Your phones were slightly different. 3 entries changed. Balance before: Sofia +€12,40 → now: Sofia +€8,90."* Each change links to the entry in Details.

### Step 5 — Old links after the upgrade (R4)

v3/v4 links always need the answer typed in, because v1 encryption salts per link and v2 doesn't store the raw answer.

| Phone state | What an old link does |
|---|---|
| Migrated, handshake with the sender done | Nothing changes: *"This is a link from before the upgrade. Your tally is already up to date."* |
| Migrated, no handshake yet | Updates the **provisional copy of the sender's entries only**, and only if the link is newer than the current copy (newest ID timestamp). Never touches my own entries. |
| No tally on this phone | Creates a migrated tally from the link, as a fresh device would. My own entries in it are adopted as my legacy log. |
| Different question or names | *"This link is for a different tally"* → join it as a separate tally. v2 supports several tallies, so nothing is overwritten. |

v3/v4 import code stays in v2 for **at least 2 years** (step 6). It's small, and chat histories don't expire.

### Step 6 — Keep conversion available for at least 2 years

People may not open Schplitz for months, so access to old tallies must not expire on a schedule they can't see.

- **Automatic migration on first load stays.** Most people never need to look for anything.
- **Plus a permanent option: Settings → Bring in an old tally.** It accepts:
  - **the old data still on this phone**: re-runs the conversion, and also picks up anything a v1 tab added later;
  - **an old share link (v3/v4)**: the most important source, because **every v1 link is a full copy of the tally**;
  - **pasted text** from v1's text export;
- **Converting is repeatable and safe.** Everything is matched by v1 expense ID, so bringing in the same tally twice, or an older copy, never duplicates or overwrites (same rules as step 5).
- **`schplitzExpenses` is kept untouched for at least 2 years** after v2 ships. Review then, not sooner. Until it's removed, a rollback to v1 still works, but entries added in v2 won't appear in v1. Say this in the release notes.
- **Plain-text answers (A2)** are still deleted immediately at migration (step 1.6). Keeping the data is fine; keeping a plain-text secret isn't.
- **Safari caveat:** on Safari, the old data on the phone can be deleted by the browser itself, regardless of what we keep (R10, [v2.0.md §4.1](v2.0.md#41-browser-storage-on-iphone-and-mac-safari)). That's why old links matter: the last v1 link in a chat can rebuild the whole tally.
- **Deployment:** v2 must ship on exactly `https://schplitz.com`. If `www.` was ever served separately, add a redirect only **after** checking whether people have data there; redirecting doesn't move storage (R9).

## 3. Testing

- **Fixtures from real v1 code.** The v1 sources are in git, so tests can import the v1 `utils.js` to produce genuine v3/v4 links and A1/A2 storage objects instead of hand-written approximations.
- **Two-phone simulation:** migrate phone A and phone B independently from diverged states → exchange first links → assert **identical state on both** and a balance equal to v1's balance with the same rates (within one cent per entry).
- **Divergence cases:** unshared additions on each side; Sofia deleted her own entry; Sofia deleted *my* entry (v1 allowed this); one phone wiped; one phone never imported anything.
- **Old links:** an old v4 link after the handshake, before the handshake, on an empty phone, and for a different tally.
- **Answers:** wrong answer at the handshake (mismatch message), A2 device (silent derivation and answer deleted).
- **Edge data:** AED/ALL entries, amounts with more than 2 decimals, invalid expenses, unknown `paidBy`, unicode names, identical names.
- **Rollback:** v1 still loads its untouched key after v2 has run.
- **Bring in an old tally:** from each source (device data, v3 link, v4 link, text), twice in a row, and an older copy after a newer one: no duplicates, nothing overwritten.
- **Sorting:** a group remap produces one `recat` entry, syncs, and shows the new category on the other phone; the other person's entries can't be remapped.
